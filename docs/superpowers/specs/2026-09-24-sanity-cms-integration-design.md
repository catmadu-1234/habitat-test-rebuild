# Sanity CMS + Visual Editing integration: design

Status: draft for review, 2026-09-24. Branch: `homepage-rebuild`.

## 1. Goal and success criteria

Make the Habitat Learn homepage editable in Sanity, including click-to-edit visual editing (Presentation tool),
without changing how the page looks.

Success means:

1. An editor can change any visible string, `alt`/`aria-label`, image, and outbound link on the homepage in Sanity,
   see it live in Presentation, publish, and see it on the deployed site without a code deploy.
2. Blog cards are `post` documents editors can add, edit, and reorder by date.
3. After migration the site is visually identical to today's build at 1440 / 820 / 390px (section heights from
   CLAUDE.md still hold) and `npm run build`, `npm run lint`, and `npm run cf:build` pass.
4. Layout, Tailwind classes and design tokens stay in code and stay Onlook-editable.

## 3. Architecture

```
habitat-rebuild-test/
├── app/  components/  lib/  ...   existing Next.js app (unchanged layout: not moved to web/)
├── sanity/                 NEW: client, live.ts (defineLive), image.ts (urlFor), queries/, token.ts
├── sanity.types.ts         NEW: generated by TypeGen, committed
(sibling folder ../studio-habitat-learn-test: the standalone Studio, its own repo, with scripts/seed.ts (one-time JSON -> Sanity import) and scripts/verify-seed.ts, deleted after cutover)
                            These live in the Studio because `sanity exec --with-user-token` must run inside the Studio project.
```

- **Studio** and **site** are separate apps that share only the Sanity project. Each has its own `node_modules`.
- **Site data flow:** section component -> `sanityFetch({ query })` -> published content for visitors, draft content
  when Draft Mode is on. `<SanityLive />` in the root layout keeps content fresh; `<VisualEditing />` renders only in
  Draft Mode.
- **Presentation:** Studio embeds the site in an iframe (`previewUrl.origin` = site URL, enable route
  `/api/draft-mode/enable`). The site must not send `X-Frame-Options`/`frame-ancestors` restrictions (it sends none today).
- **Repo hygiene:** the Studio is a separate repo, so the site's `tsconfig.json` needs no exclude; ESLint ignores `scripts/**` and
  generated `sanity.types.ts`, and Prettier ignores `docs/`.

### Cloudflare/OpenNext risk and the spike (first task in the plan)

The site is fully static today and `open-next.config.ts` (`defineCloudflareConfig()`) has no incremental or tag cache,
so a publish in Sanity could never reach the deployed site without a redeploy. Findings from reading `next-sanity@13.3.4`
and `@opennextjs/cloudflare@1.20.6`:

- `next-sanity` 13 peers on `next ^16` and `sanity ^5.29 || ^6`, so it is compatible with this stack on paper.
- Its `defineLive` has two implementations. The Cache Components one (`cacheTag`/`cacheLife`) needs
  `cacheComponents: true`, which Next documents as Node-runtime-only; we do **not** enable it. The other
  (`cacheComponents: false`) uses `fetch(..., {next: {tags}})`, reads Draft Mode itself, and turns stega on in Draft
  Mode when the client has `stega.studioUrl`. This design uses the second.
- OpenNext ships KV/R2 incremental caches and KV/D1 tag caches. We use **KV for both** (no schema to manage). The KV tag
  cache is documented as eventually consistent (up to ~60s) and experimental; acceptable for marketing copy.
- v13 removed APIs the Sanity skill's reference still shows (`useDraftModeEnvironment`, `tag`, `stega` on
  `defineLive`); the plan uses the v13 names (`useVisualEditingEnvironment`, `requestTag`, `stega.studioUrl` on the client).
- Live updates in v13 are "less live" by default: without a sync-tags function, other visitors may need a refresh to see
  a publish. We add a signed `/api/revalidate-tags` route plus a Sanity function/webhook to close that gap only if the
  spike shows it is needed.

Before building on approach A, the first task is therefore a gated spike on `npm run cf:preview` (real Workers runtime):

1. `next build` succeeds with `cacheComponents` unset and the non-Cache-Components `defineLive` is the one that loads.
2. `sanityFetch` returns published data in the Worker; images from `cdn.sanity.io` optimize through the `IMAGES` binding.
3. With the KV caches bound, a publish in Sanity shows up on the deployed site (within the KV consistency window).
4. `/api/draft-mode/enable` sets the bypass cookie and Presentation loads the site with overlays and click-to-edit.
5. The Worker bundle stays under the platform size limit.

If 1-3 fail, fall back to approach B (own `fetch` tags + signed webhook + `revalidateTag`, same KV caches), which only
swaps the `sanity/lib/live.ts` module. Creating the KV namespaces changes Habitat's Cloudflare account, so the plan
stops for explicit confirmation before running `wrangler kv namespace create`.

## 4. Content model

Modelling rule: **mirror the current JSON shape** so component diffs stay small (`t("hero.title")` becomes
`hero.title`). Use arrays only where an editor should add/remove/reorder items; use named objects where the layout
depends on a fixed set (nav, footer). Every image field has `hotspot: true` and a required `alt` sub-field
(`alt` replaces the current `*.imageAlt` strings).

**Singletons** (fixed IDs, created by the seed, pinned in Studio structure, hidden from "New document", delete and
duplicate disabled): `homePage-en` and `siteSettings-en`. Each has a hidden read-only `language` field. The
`<type>-<lang>` ID convention follows Sanity's localized-singleton pattern so a second language later is a new
document plus the document-internationalization plugin, not a migration. That plugin is not installed now.

### `homePage` (field groups/tabs: Hero, Values, Products, Blog, Contact)

| Section | Fields |
| --- | --- |
| `hero` | label, title, description, primaryCta, secondaryCta (button labels; URLs come from `siteSettings.links`), trustedBy, pauseVideo, playVideo, `avatars[]` (image+alt), teamImage (image+alt), followUp (title, message, sentBy) |
| `values` | label, title, image+alt, `items[]` (title, description) |
| `products` | label, title, description, learnMore, and three **named** items `messengerPigeon`, `podium`, `liveServices` (title, description, image+alt each). Named, not an array, because the card stacking offsets and link targets are tied to each product in code. |
| `blog` | label, title, nextPage (aria-label). Cards come from `post` documents, not from this object. |
| `contact` | title, description, partnersLabel, `partners[]` (logo image+alt), form (name/email/message labels + placeholders, submit) |

### `siteSettings`

`meta` (title, description, ogImage), `nav` (logoAlt, menu labels, every nav/promo label + description, mirroring the
current `common.json` nested shape), `footer` (logoAlt, four columns, social aria-labels, copyright), and `links`.

**Links:** one named URL field per entry in today's `lib/links.ts` (about 25). Components read
`settings.links.bookCall`, etc., so each URL is edited in one place even though it appears in several places
(nav, mobile menu, footer, CTAs). `lib/links.ts` is deleted after the seed reads it. *(Flagged for review: the
alternative is to keep `lib/links.ts` code-managed and only make copy/media editable.)*

### `post` (blog card)

`title`, `category`, `date` (Sanity `date`; cards show month and year only, e.g. "Aug 2026", formatted in code), `image`+alt,
`url` (external link, as posts live on the Webflow blog today). No slug or body: YAGNI until blog pages are rebuilt.
Homepage query: `*[_type == "post"] | order(date desc)[0...3]`.

### Stays in code (not editable)

Hero background video (`public/video/`; Sanity `file` assets must not serve production video), fonts, favicons,
UI icons (SVG), the decorative `grow.png`, all Tailwind classes and tokens, and section order/layout.

## 5. Frontend changes

- **New `sanity/` module:** `client.ts`, `live.ts` (`defineLive`), `image.ts` (`urlFor`), `token.ts` (throws if the
  read token is missing), one file of `defineQuery` queries per section (unique query names for TypeGen).
- **Section components** stay async server components and keep their markup and classes. Each fetches its slice
  (`*[_id == "homePage-en"][0].hero`) instead of `getTranslations`. Nav/Footer/metadata fetch `siteSettings-en`.
- **`components/ui/SanityImage.tsx`:** wraps `next/image`, keeps the existing `fill` + `sizes` + `quality` props,
  builds the URL with `urlFor`, applies LQIP and hotspot (`object-position`). `next.config.ts` gains
  `images.remotePatterns` for `cdn.sanity.io`.
- **Layout:** render `<SanityLive />`; in Draft Mode render `<VisualEditing />` and a small "Disable Draft Mode"
  button. Add `app/api/draft-mode/enable/route.ts` (`defineEnableDraftMode`).
- **Stega rules:** `generateMetadata` and any string used for logic (URLs, `variant`s, keys, `lang`) use
  `stega: false` / `stegaClean`. Rendered text and `alt` are left alone in Draft Mode only.
- **Removed after cutover:** `next-intl` (plugin, `i18n/request.ts`, `getTranslations`, `SITE_LOCALE`),
  `locales/`, `crowdin.yml`, `lib/links.ts`, and the `public/images/**` files that moved to Sanity. `<html lang>`
  comes from a single default-locale constant.

## 6. Studio

- `schemaTypes/{documents,objects}/`: kebab-case files, one exported const per schema.
- Structure: pinned "Home page" and "Site settings" singletons, divider, "Blog posts" list.
- Presentation `resolve.locations`: `homePage`, `siteSettings`, and `post` all resolve to `/`.
- `sanity.cli.ts` gets `typegen` config (`path` scanning the parent app, `generates: ../sanity.types.ts`,
  `enabled: true`).
- Deploy with `sanity deploy` to a `*.sanity.studio` hostname. CORS origins (with credentials): `http://localhost:3000`
  and the deployed Workers URL.

## 7. Migration and cutover

1. **Seed script** (`sanity exec scripts/seed-sanity.ts --with-user-token`, so no write token is stored): reads
   `locales/en/*.json` and `lib/links.ts`, uploads the referenced images from `public/images/**` (Sanity dedupes by
   hash, so re-runs are safe), and `createOrReplace`s the two singletons and the three posts. Live-site typos in
   `home.json` (`thatremoves`, `highquality`, `empowerstudents`, `toreach`) are seeded verbatim so the migration is a
   no-op visually; editors can then fix them in Sanity, and the CLAUDE.md "known deviations" note is updated.
2. **Round-trip check:** a script fetches the documents and asserts every original JSON key/value is present.
3. **Switch components** section by section, running the site against the seeded dataset.
4. **Visual verification:** Playwright screenshots (as in earlier sessions) of before/after at 1440, 820, 390 plus the
   section-height table in CLAUDE.md. Any diff blocks cutover.
5. **Cutover:** delete the removed items listed in section 5, then update `CLAUDE.md` and `README.md`.

## 8. Rules that change in CLAUDE.md

- Rule 2 ("no hard-coded text; lives in `locales/*.json`") becomes: all copy comes from Sanity; no hard-coded
  user-facing strings in components.
- Rule 4 ("local assets only") becomes: CMS-managed images come from the Sanity CDN via `next/image`; static UI
  assets and video stay local. Never hotlink Webflow's CDN.
- "Outbound links live in `lib/links.ts`" becomes: links live in `siteSettings.links` or on the document they belong to.
- "Adding a language" and the Crowdin section are replaced by a short note on adding a locale in Sanity.
- New: run `sanity typegen` (or `npm run dev` in the Studio folder) after query or schema changes.
- Known trade-off to document: Onlook edits classes only; text edits are made in Sanity, because text no longer
  lives in the JSX or in JSON.

## 10. Testing strategy

- Build gates: `npm run format`, `npm run lint`, `npm run build`, `npm run cf:build`, `studio` `npm run build`.
- Round-trip content check (section 7.2) and visual comparison (7.4) are the main regression tests.
- Manual Presentation smoke test: click a heading, edit, see it update live, publish, confirm it on the deployed site.
- Draft Mode must not leak: confirm a logged-out visitor sees only published content and no stega characters in
  page source or `<head>`.

## 11. Out of scope

Page builder / reordering sections, additional languages, blog detail pages, a real contact-form backend,
Media Library or Mux video, editor roles and permissions, scheduled publishing, and moving the deployment to
Habitat's own Cloudflare account.
